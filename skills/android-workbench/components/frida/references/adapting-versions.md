# 新增版本适配

通用流程可处理新设备和候选版本，首版内置构建/资源适配器只支持 `17.18.0`。遇到其他版本时应完成适配工作，而不是改 profile 的版本号绕过检查。

1. 锁定官方 tag/commit 和子模块，在目标设备建立所需功能的原版基线。核对该版本上游的构建入口、主机支持、SDK/NDK、Python/Node/Vala 等依赖及预编译资源来源。
2. 根据修改意图在当前源码重新定位入口和依赖。检查客户端/server/Agent/Gadget、生成 DEX/ELF 和嵌入步骤。对需要保留的协议/符号写清边界。
3. 在独立树中修改，按目的导出 patch，记录预期 commit、patch 哈希、生成资源的输入和验证办法。跨版本不沿用 `17.18.0` 的文件位置、64 字节字段或预编译 ELF 哈希。
4. 扩展构建/资源适配器，新增版本分支及真实工具链检查；不能把“不支持”改为默认走旧版路径。测试清理、缓存失配与失败后的记录。
5. 同步适配探针。模块导出 API 和 Java bridge 提供方式可能改变。记录兼容探针的哈希，保持原版与改版测试语义一致。无法执行探针时标记受阻。
6. 从干净源码重建，在目标设备完成必需能力和指定修改项验证，记录新案例的环境、来源和限制。未经对应实机验证的版本/ABI 维持待验证状态。

新 profile 只应携带实际需要的补丁与验证资源。不要复制完整上游源码、完整编译产物或私人设备证据到插件。
