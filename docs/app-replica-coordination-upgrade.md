# 复制协调流程更新

本文记录 `coordination_protocol:1` 的历史更新。当前版本为 2；执行升级与验收时，以[执行流程更新](app-replica-execution-upgrade.md)中的协议版本和步骤为准。

本次修改减少分析和交接中的重复工作，不修改 Avola 的业务实现，也不把工具测试当成 App 与原版一致的证据。

## 改动、目的与边界

| 观察到的问题 | 本次改动 | 预期作用 |
| --- | --- | --- |
| 简单空接口也依次启动范围分析、结构设计、代码实现三个工作回合 | 新增 `scope.class.publish`，允许具备完整声明证据、配置匹配且没有其他结构负责人的分析任务同时发布结构，再交给 Sol 实现 | 符合条件的类从三个工作回合减为两个，少一次重新读取和交接；复杂类仍保留独立结构任务 |
| Main 在普通交付后重复读原版、检查散列，且 `status --task` 实际计算全部任务的状态 | 单任务查询仅检查当前任务及其所用依赖；Main 复用程序结果与责任人的检查记录，有具体变化或缺口才补查 | 减少无关文件检查和重复分析；语义自查、失败与未知项仍保留 |
| 已确认结束后，停止登记与下一项预约分成多次协调 | 新增 `native-next --stopped-file`，在同一派发锁下登记真实停止并预约下一项；省去没有恢复动作时的第二次全局状态查询 | 减少结束到下一项派发之间的操作；未确认结束的线程继续占用名额 |

程序校验文件散列、版本、依赖和检查状态，不能自动判断声明是否完整或代码语义是否与原版一致。结构和实现责任人仍须进行相应比较。记录“已提交”不会自动变成“线程已停止”。

新增状态字段为 `coordination_protocol:1`，`delivery_protocol:2` 和工作区 schema 2/3 不变。不修改旧任务负责人，不批量转换记录，不因升级重跑已完成的方法。已有其他结构负责人时，继续由原负责人处理。

本次没有承诺实际提速比例。少一个工作回合不代表整个 App 快三分之一；最终效果还受任务复杂度、模型响应、构建和真正阻塞影响。切换后应比较简单类工作回合数、Main 重复分析次数，以及**实际确认停止到下一项预约**的间隔。提交到停止的时间包含线程正常收尾，不能全部算浪费。

## 如何应用到正在复制的会话

工具代码发布与当前会话采用是两件事。维护者在独立 worktree 修改、测试和推送；活动会话所用的 checkout 保持原版本，避免运行到一半混用规则。

由当前复制 Main 在任务交接点完成切换：停止派新任务，让工作者保存并结束；核对真实停止后备份当前工程与记录；快进项目实际绑定的 Workbench checkout；重新读取角色说明、重启确实加载了旧代码的常驻执行器，再恢复原来的单一调度器。无需重做 App、原版分析或重建所有任务。

本机仅更新 Workbench 源码时，升级前需要的是已验证的当前本地备份：完整分片及整包散列、文件清单、最新源码/状态、停止记录和实际备份位置。若这些均已保存并核验，远端 Release 上传失败可以单独登记待办，不应继续阻塞可逆的工具源码切换。远端上传成功与否仍如实报告；不把本地备份称为已完成远端交接。涉及换机、删除原目录、重建存储或用户明确要求先有远端备份时，不适用此项。

在恢复复制前，先收尾或暂停会写 App Git、`migration` 清单的旧发布器，避免并发改动；后续从已经冻结并核验的同一包补传，沿用原唯一 Git 保存入口。不得为续传再次捕获整个工程，也不得覆盖升级后产生的新记录。

若有尚未启动的预约，先用宿主记录核对它确实未启动，再通过原有 `run.stopped`、`outcome:launch_failed` 和实际未启动依据结束该预约；不能直接删记录，也不能伪造进程停止证明。若已经启动或无法确认，按实际运行的收尾/恢复流程处理。若存在无法确认的写入者，保持暂停，不能用升级释放名额。

单独记录因本次切换而取消的未启动任务 ID。升级后，满足原前置条件的这些任务通过 `task.resume` 携带切换原因和真实证据恢复到队列；不创建替代任务，不把历史失败也批量重试。仍缺前置条件的任务保留具体阻塞。

直接调用源码 `scripts/app_replica.py` 的每次命令会加载该 checkout 的程序，后续 `native-next` 会生成新版角色提示。**Main 自己仍须主动重读新规则；旧子线程已收到的提示不会自动改写。** 恢复线程时，以新指令中给出的角色规则为准。若入口使用安装副本或常驻服务，则按现有升级流程确认实际副本和共享工作收尾；仅 `git pull` 不能证明运行副本更新。

详细备份、真实停止、安装版更新及失败处理沿用 [交付流程升级指南](app-replica-delivery-upgrade.md)。不要用审计者旧 Release 快照覆盖仍在更新的工程。

## 可发给当前复制会话的提示词

把 `TARGET_COMMIT` 替换成维护者交付的完整提交号。以下是一条连续执行任务，不要求每个正常步骤重新询问用户。

```text

先停止新的 native-next/宿主派发，不中断正在写入的工作者。让活动任务在稳定边界保存源码、检查结果、未完成事项和继续位置，并正常提交或保存等待检查点。核对宿主实例及其写入后代真实停止，再用现有 run.stopped 登记。尚未启动的预约仅在真实宿主记录证实未启动时用 outcome:launch_failed 及该证据结束；单独记录因切换而取消的任务 ID，供升级后恢复。已启动或未知就按运行收尾/恢复流程处理，不能为清空占用伪造停止。提交通过、文本说完成或超时都不是停止证明。还有无法确认的写入者就保持暂停并报告，不启动替代写入者。

保存当前机器最新的 App 源码和 workflow 记录，保留失败与未知项。按项目已有方式备份；Avola 若使用 migration/sync.py，则按其说明运行 --require-idle 并核对快照、远端结果和 handoff_ready。仅更新本机 Workbench 源码时，完整本地包、分片/整包散列、清单、最新源码/状态和停止记录均已核验即可继续；远端上传失败单独保留待办，不反复等待网络而阻塞切换，不宣称远端备份成功。先收尾或暂停会修改 App Git/migration 清单的发布器，再恢复复制；后续只补传同一冻结包。不得用旧 Release 覆盖当前目录，不 reset、不 clean。

核对 workbench.project.json、workflow/project.json 和正式路径绑定，确定实际使用的 Workbench checkout。确认工作树和 Git 分支状态，git fetch origin 后，在可快进且无本地修改冲突时 git merge --ff-only TARGET_COMMIT。若已含该提交则核对即可；有分叉或本地改动时保留现场并报告，不强制覆盖。

读取新 checkout 的 docs/app-replica-coordination-upgrade.md、组件 README，以及 agents/app-replica/main.toml、app.toml、analysis.toml、class.toml。运行 python3 scripts/check.py，claude 可用时运行 claude plugin validate .。确认实际入口使用这个 checkout；重启加载了旧程序的常驻执行器，安装副本按原升级指南处理，不能影响其他共享设备任务。

使用实际源码入口 status --summary，确认 coordination_protocol:1、delivery_protocol:2、occupied:0，核对原任务、负责人、失败/未知项和后续待办仍在。不要批量迁移或重跑旧方法。

恢复原有单一调度器、原模型和并发限制。仅对本次切换取消、尚未启动且前置条件已满足的任务，用 task.resume 携带切换原因和证据恢复原任务；历史失败不批量重试，前置条件未满足的仍保留阻塞。普通交付用 status --task 和责任人的检查记录，有具体变化或缺口才重查。简单类已有完整声明证据且未指定其他结构负责人时，让原 analysis/scope 使用 scope.class.publish，随后由 Sol class/code 实现；不为测试强行制造这种任务。确认宿主和写入后代结束后，使用 native-next --stopped-file 登记真实停止并预约下一项，执行返回的宿主动作并登记实际 run.started；recovery:true 先核对，不能重复启动。

先观察一个本来就应推进的任务交接，核对新提示、有效交付依赖、停止证据、下一次预约和唯一写入者，再继续。报告实际工具提交号、备份位置、两项协议字段、采用的任务/运行 ID 和首轮结果。分别报告实现、构建、安装、运行与原版核对；工具更新成功不代表 App 已完成。
```

## 验证范围

回归用隔离的临时工作区与明确标注的宿主观察，覆盖合并后两次工作运行、既有负责人冲突、配置不匹配、证据/类版本变化、未通过检查、活动线程占位、单任务传递依赖、停止证明拒绝、预约重试和搬迁路径。完整检查使用 `python3 scripts/check.py`，另核对插件。

工具测试不执行真实模型或 Android 场景。当前复制会话的采用和速度变化，须以它完成上述切换后的运行记录为准。
