# 执行清理、路径清单与相关类复用

本次更新的 `coordination_protocol` 为 **2**，`delivery_protocol` 仍为 2，工作区存储 schema 2/3 不变。既有任务不批量迁移，不重跑已完成的方法。源码、安装副本、常驻共享服务和复制会话是否采用，须分别核对。

## 共享工具退出与超时

工具代理把获取环境的等待也纳入收尾范围，处理正常输入关闭和 SIGTERM；一次取消、记录或释放调用失败不会跳过其余清理。只有明确的传输故障且请求可重复执行时才重试；重复 MCP 结果记录必须与原请求内容一致。调用已转交但没有完整结果时保留 `partial`，不因物理资源已释放就宣称功能成功。

服务分别核验工具拥有者、上游进程组和仍活跃的后代，区分存活、确已退出和未知。拥有者正常收尾后，`leases.close` 持久记录已核验的进程树关闭，随后释放；释放重试仍检查当前存活/未知进程。读取服务超时与拥有者异常退出是不同失败，不能仅凭相似症状认定一个根因。管理队列回归同时核对清理状态与后续排队任务实际启动。

SIGKILL 等无法执行收尾的退出，以及进程身份无法读取的情况继续保留故障占用。旧的未释放记录如果没有已核验的关闭凭据，不能靠“根进程 PID 已消失”自动清理；子进程可能已脱离原进程。正式 `environment.recover_host_lease` 只在关闭凭据及当前进程检查都足够时恢复，不删除未知锁。拥有者仍存活时出现的新后代也会阻止释放。

如果最初提交请求的全部响应均不可取得，即使重试使用同一 `request_key`，客户端也可能不知道服务已创建的任务 ID；这种持续传输故障仍保留不确定结果。修复不保证服务永不超时，也不把历史未核实的故障改成成功。原有无关故障记录保持原样。

## 提示中的完整路径清单

每次启动生成完整、不可变的输出清单：`coordination/prompt-manifests/<SHA256>.json`。提示给出相对当前 workflow 的路径、格式版本、字节数及 SHA-256；读取时核验这些字段。清单包含每条原始路径及本次绑定后的有效路径、任务 revision、运行记录散列、路径绑定 revision、变化基线和增减项。运行本身没有递增版本字段时 `run_revision` 为 `null`，不虚构版本。

`coordination/prompt-manifests/runs/<RUN>.json` 保存该运行生成过的全部清单引用。首次任务运行展开全部输出；后续展开新增项及显式选择的当前输出。`native-next --focus-output RAW_PATH` 可重复传入，必须精确匹配任务已有的原始输出身份；不能用父目录、搬迁后的别名或未登记文件扩权。它只控制提示展示，不改变任务、文件负责人或提交必须覆盖的输出。

旧运行没有清单时，提示明确说明没有可核验的变化基线，提供完整清单、当前检查点和消息入口，不把历史路径当作新增项。恢复线程和新线程都不能假定记得旧清单。损坏引用会失败；路径搬迁后重新解析当前路径，旧有效路径只是历史记录。任务后来登记的新输出仍以协调状态和解析器为准。

## 相关简单类共用线程

保持每个原类的原对象、逻辑结构负责人、源码写入者、依赖和交付结果。Main/App 在有实际关联证据时，用 `task.group` 登记尚未启动的同角色任务；它们依次使用同一个原生线程。Astra 的范围/结构组和 Sol 的代码组分别安排。不会把正在工作或曾经分配过执行线程的任务强行并入另一线程。

```json
{
  "op": "task.group",
  "request_id": "related-class-group-v1",
  "group_id": "related-callbacks-code",
  "task_ids": ["TASK_A", "TASK_B"],
  "reason": "两个简单回调来自同一调用链，复用已核验的捕获字段和注册表材料",
  "relationships": [{
    "from": "TASK_A", "to": "TASK_B", "relation": "同一调用链中的相关回调",
    "evidence": [{"path": "artifacts/callback-relations.json", "sha256": "ACTUAL_SHA256"}]
  }]
}
```

组内所有成员必须有可连接的关系及实际文件散列，配置的角色、模式、模型和强度必须完全一致。程序检查连接和证据身份；是否确实适合成组仍由负责规划/结构的人判断。组没有人为数量或上下文额度上限，不能只因类名相近就合并。组记录不可变，重试沿用原请求 ID；各任务的文件权限不合并。

`native-next --group GROUP --external-active N` 选择组内真正就绪的一项。前项实际提交/保存检查点、宿主及写入子进程结束、`run.stopped` 成功后，后项才能启动。可同时使用 `--stopped-file`。匹配的已停止原生 handle 返回 `followup_task`，否则返回正常的新建指令；已有预约仍按 `recovery:true` 先核对，不能重复启动。单项失败或未知不会变成整组通过，也不会使后一项绕过原依赖。CLI 执行后端暂不支持组内线程复用。

同一线程可以复用分析步骤和检查格式：先核对原类映射及来源散列，再对照声明、继承字段归属、初始化顺序、普通方法及实际 native 声明，最后记录候选源码检查和下游构建/运行待办。每类仍有独立结果。共享只读证据可直接引用；足够时使用一个完整报告/检查产物，不为每个空接口复制一套文件。不把模板中的空项视为通过，不删除真实未知或失败。

这个实现减少新建线程和重复读取，不减少每类的正式生命周期回执。宿主样例证明一次新建加一次续跑可处理两个独立任务，不能据此宣称真实模型回合减少、App 加速或 Android 等价。采用后在自然出现的相关类组记录实际新建/续跑数、耗时和返工，禁止为统计重做已完成类。

## 升级与验证

先停止新的复制派发，让当前写入者收尾并记录真实停止，保存最新本地备份。用独立工作树实现和检查，快进实际绑定的源 checkout；共享服务只在其真实活动工作结束后通过 `scripts/upgrade_runtime.py --project PATH --skip-project-update` 切换。旧常驻代理还可能持有旧代码，须核对其退出或重新连接，不能把 Git 更新当作热替换。

使用新源码查询 `status --summary`，确认 `coordination_protocol:2`、`delivery_protocol:2`，原任务、负责人、未知项和待办保留。在写入组记录后不可混用不认识组约束的旧调度程序。重新读取组件及角色说明，再由原唯一 Main 恢复一个确有工作要做的任务，核对实际新提示、完整清单、宿主配置和停止证据。

必需检查为相关回归、`python3 scripts/check.py`、`python3 scripts/build_plugin.py --check`，以及可用时的 `claude plugin validate .`。测试里的管理队列及进程样例验证工具行为，不代表设备或复制 App 验收。
