# App 复制过程中的 Git 保存方案

日期：2026-10-17，2026-10-18 更新接入记录。状态：本地自动保存与服务批量推送已实现，并已在现有 Avola 项目启用；验收记录见本文末尾。用户要求以当前复制场景的实施负担为优先判断标准，避免为了使用功能而引入设计。本版替代此前偏重的异步快照与发布流水线方案。

## 目标与已确认决定

| 项目 | 决定 |
| --- | --- |
| 保存范围 | 被复制 App 的源码、资源、构建配置；现有累积的这些改动一起进入首次保存 |
| 工作方式 | 共享一个实际检出在 `replica/<project-id>` 上的工程目录，沿用最终文件唯一写入负责人 |
| 保存时机 | 稳定的工程文件组装、任务交付及长任务中间进展；允许暂时不能编译 |
| 推送阈值 | 默认累计 5 笔未推送提交，或最早一笔等待 10 分钟，先到者触发；可配置 |
| 后续阶段交付 | 验证通过后自动发布到开发分支，每阶段一笔提交；细粒度历史留在复制分支 |
| 交互成本 | 合理默认值直接采用，不为普通提交、推送和明显的实施选择逐次询问 |

现有角色和复制流程见 [复制编排设计记录](app-replication-redesign.md)，术语见 [领域术语](../CONTEXT.md)，分支取舍见 [ADR 0001](adr/0001-replica-progress-and-stage-history.md)。本功能不增加 Agent，不改变上下文额度。

## 自审：哪些负担值得付出

当前流程已经有最终文件唯一写入负责人、文件组装、交付、等待和实际停止边界。同步完成一次本地 Git 提交，就能利用这些边界保证待保存文件暂不变化。没有必要先将同一份源码复制进第二套存储，再排队提交。

| 设计 | 对当前场景的判断 |
| --- | --- |
| 稳定文件组一起提交 | 保留：符合现有组装方式，不要求每个方法单独操作 Git |
| 仓库范围的本地提交锁 | 保留：多个任务共享同一个 Git 仓库，提交必须串行 |
| 独立不可变快照库、异步提交队列 | 移除：同步提交成功后 Git 本身就是不可变版本；不再维护两份源码状态 |
| 手工构造提交、更新 HEAD、修复默认 index | 移除：优先使用 Git 自己的按路径提交语义，避免自建 Git 事务 |
| 新常驻进程、服务管理器、通用任务队列 | 移除：定时推送挂入已有 Workbench 服务生命周期 |
| 每个 Agent 的 worktree | 不采用：现有唯一写入负责人已经解决主要写入归属问题 |
| 每次保存都构建、运行或调用模型生成摘要 | 不采用：保存允许不完整版本；简短提交信息从任务和事件生成 |
| 完整自动阶段发布流水线与备份捆绑上线 | 不采用：阶段发布是后续独立交付，不阻塞提交和推送能力 |

这里的简化有明确代价：写入负责人需要等待一次本地 Git I/O；提交失败前的编辑没有额外快照副本。应如实显示未保存状态，不能为了宣称无损保存而重新引入整套事务设施。临时工程的实测耗时见验收记录，不构成所有真实工程的时延承诺。

## 最小实现：一个提交入口，一个推送检查

### 在已有边界同步提交

1. 最终文件负责人完成一次稳定组装或编辑后，调用统一保存入口；交付和等待入口复用它。相关文件一起提交，方法片段只有在组装进工程后才纳入这套 Git 历史。
2. 负责人及其写入后代在调用返回前不改动这一组文件。其他负责人可以继续编辑各自文件。取得仓库锁后，只处理明确的工程文件列表，包括新增、修改和删除，不执行全目录 `git add .`。
3. 使用 Git 标准的按路径提交能力：先登记所需新文件，再按确切路径提交，例如 `git commit --only -- <paths>`。实际实现须使用参数数组、字面路径及必要的 NUL 分隔，不能将文件名拼成 shell 命令。无需自管私有索引与 HEAD/index 双写恢复。
4. 无变化不创建空提交；成功后返回真实提交 OID。任务与事件标识写入提交信息，用于追溯和应答丢失后的核对，不再增加独立快照数据库。
5. 在确认实际写入者已停止、但尚未允许续跑改写文件时，可以通过同一入口作最终兜底。Git 调用在复制状态锁外执行，设明确超时；失败应记录并继续完成实际停止处理，不能因网络或 Git 故障长期扣住执行名额。
6. 提交失败保留工作目录，显示原因，在下一次稳定边界重试。遇到无法确认的人工 Git 操作、合并或锁冲突时暂停自动 Git 写入；不自动重置文件、清除索引或删除来历不明的锁。能确认只是应答丢失且提交已经存在时复用该提交。
7. 保存结果不改变任务的语义修订，不把 Git 成功当成任务完成、构建成功或 MVP 通过。

按路径提交可保留其他路径的人工暂存；本次文件若存在冲突的人工暂存版本，则不能擅自覆盖。对同一文件的并发人工修改仍违反现有唯一写入负责人约定，自动提交不另建一套编辑器来解决它。

现有 `task.submit` 后运行仍可修正文件，因此不能等任意后台时刻再读取原路径。同步保存使调用期间的稳定内容直接进入 Git，避免这个竞态。中间保存仍需要写入负责人调用；计时器不能判断半写文件是否已完成。

### 用已有服务按阈值推送

- 在现有 Workbench 服务中增加轻量的推送检查，执行逻辑留在独立 Git 模块。复用服务启动、退出和健康状态，不另建 daemon、消息队列或 Agent。
- 服务每 5 秒检查数量和时间阈值。网络推送在后台执行，不能阻塞现有设备调度循环、持有队列项目/设备锁，或让写代码的 Agent 等远端。
- 根据 Git 历史和少量本地配置/状态计算未推送数量与最老等待时间。重启后不清零计时；没有待推送提交不访问网络。定时检查只读必要 Git 信息，不反复扫描所有源码、证据或 APK。
- 每次推送固定一个已存在的提交 OID，仅更新配置的复制分支，使用普通快进推送。期间的新提交留给下一轮，任务正常结束时额外尝试刷新。
- 断网或超时后退避重试。下一次正常推送和远端核对即可判断历史是否已经到达，不为代码备份另建“恰好一次”消息投递协议。未知结果不显示为已同步。
- 权限、分支保护和历史分歧明确报告；不自动强推、rebase 或在活跃工程目录合并。本地提交继续可用。
- 10 分钟是服务健康时的触发阈值，加上检查周期和网络耗时；不是离线时限，也不是尚未提交编辑的最大年龄。服务未运行时显示定时推送不可用，沿用已有服务的启动方式，不悄悄声称定时保障存在。

源码依据：现有 [service.py](../workbench/service.py) 已有常驻服务与调度循环，[cli.py](../workbench/cli.py) 已有服务启动入口；[runner.py](../workbench/app_replica/runner.py) 的原生调用本身没有定时循环。复用服务不等于把 Git 推送包装成占用设备队列的任务。

## 必须保留的范围与接入约束

- 明确实际 App 仓库、工程路径、复制分支和远端；沿用已有配置，不能猜测目标仓库。接入正在执行的任务时，在现有写入边界形成首次稳定保存，保留当前累积源码。Workbench 自身的开发修改不纳入。
- 排除 APK、设备标识、凭据、运行证据、生成环境；规则覆盖已跟踪文件，不能只依赖 `.gitignore`。图片等真正的工程资源正常保存。
- 既有 Git 祖先历史也会随分支推送；当前路径过滤不能清理历史中的已知禁止内容。未发布的禁止历史应阻止推送并报告，不自动改写历史。接入已有项目时，允许复用已在同一推送远端作为分支头发布的精确 HEAD，记录基线及目标地址校验值；后续仅校验新增历史，禁止把该例外扩展到新文件或其他远端。
- 使用 Git 返回的仓库/common directory 获取正确锁位置，支持合法的 `.git` 文件布局；配置路径遵循既有 schema 2/3 的路径绑定机制。
- 当前复制工作区、App 工程和 Workbench 源码仓库不是同一对象。Git 不备份 Agent 对话、协调状态、独立方法片段或运行证据，原工作区记录继续负责这些内容。

## 阶段发布：保留目标，单独交付

用户已经确定“验证通过后自动发布开发分支，每阶段一笔提交”。该目标保留，不能把它变成持续备份的前置条件。本轮最小实现的验收范围收缩为提交与批量推送；阶段发布随后单独实现和验收。这是实施拆分，不把已同意的自动行为改成每阶段询问用户。

阶段发布确实有额外成本，不能直接用现有 `mvp.current_result=pass` 就自动合入最新复制分支。目前 MVP 结果检查任务修订及可变产物，没有强制绑定实际待发布 Git 树和构建包。需要满足以下边界后才能启用：

- 固定一个完整候选及其全部变更来源；不能因任务 A 通过而夹带任务 B 尚未纳入阶段的半成品。优先在现有 MVP 边界封存，不建设自动拆分补丁或挑选方法的系统；范围不闭合时暂缓阶段发布，备份继续。
- 验证实际要交付的源码和构建产物，保留对应受管运行证据。源码继续编辑时，要么沿用已有阶段停写边界，要么提供一个固定验证目录；只有现有流程无法满足隔离时才增加该目录，不预先规定必须使用 worktree。
- 多次阶段发布须保留上次已交付的来源版本，以正确生成本次增量。首次保存已有源码不代表这些源码已经交付，不能因此遗漏首次发布的改动。
- 开发分支在验证期间变化时，重新生成并验证候选；只允许经过验证的快进更新，结果不确定时先核对远端。不得为了保持“一笔提交”覆盖他人的开发历史。

阶段发布的具体机制在接入现有 MVP 流程时确定。本次不为它提前引入新调度器、通用发布状态机或整套验证平台。

## 预期效果与实际负担

完成最小实现后，稳定工程进展会持续成为本地提交，达到 5 笔或 10 分钟条件后自动推送；网络故障不会阻止继续写代码和本地保存。历史可追溯到任务，已有累积代码可一次接入。

额外负担主要是每个稳定文件组的一次本地 Git 操作、一个仓库锁，以及现有服务中的轻量推送检查。不为 Git 另行调用模型，不增加每次保存的构建验证、源码副本库或 Agent 数量。长任务主动提交中间保存点仍有工具调用成本，应尽量复用原有组装与交付入口。检查状态直接并入现有状态输出：最近提交、未推送数量/等待时间、最近同步和失败原因。

代价不能隐藏：长任务若不交出稳定保存点，仍会有未提交编辑；Git 失败时保留文件并报告，但不承诺保存了失败前的每个版本；服务停机或断网时远端备份会延迟。实际实施需测量常见文件组的提交耗时，并验证慢推送不会拖慢现有设备调度。仓库已有 hook 若造成重型构建或交互阻塞，应明确处理，不能未经说明禁用，也不能视作无成本。

## 验证依据与实现验收

2026-10-17，使用本机 Git 2.53.0 和临时仓库验证了：

- 标准按路径提交可同时处理新增、修改、删除，正确保留并排除其他路径的人工暂存与未完成编辑；保存路径的默认索引没有反向差异。包含方括号的字面文件名也已验证。
- 此前私有索引方案会留下默认索引的反向 staged diff。这支持本版改用 Git 自带提交能力，无需再实现对应修复设施。
- 整个来源树会包含其中的未完成文件；首次捕获基线也不能冒充已交付版本。这些是阶段发布的真实约束，但不应扩展成基础备份的额外门槛。

Git 按路径提交依据：[Git 2.53.0 git-commit 文档](https://github.com/git/git/blob/v2.53.0/Documentation/git-commit.adoc)。新增文件先通过 [git-add 的 intent-to-add](https://github.com/git/git/blob/v2.53.0/Documentation/git-add.adoc) 登记名称，再由标准按路径提交读取稳定内容；hook 拒绝时无需修复内容暂存或重建索引。

已完成的实现验证：

- [Git 集成测试](../tests/test_app_replica_git.py) 使用真实临时仓库和本地 bare remote，覆盖文件增删改/权限/字面路径、范围排除、并发负责人、人工暂存、空提交、保存应答重试、hook 拒绝后重试、任务交付/等待/停止、计数或时间触发、离线恢复、推送应答丢失、远端分歧、慢推送期间继续保存、schema 3 路径绑定、真实服务计时以及 CLI 入口。
- 实际启动现有 Workbench 服务，在没有后续复制命令或模型回合的情况下观察到定时推送到临时远端；慢推送测试确认不占提交锁或设备调度线程。两者均未使用真实设备。
- 本机 Codex CLI 0.163.0 `codex sandbox -P :workspace` 中，按现有布局从包围目录执行真实保存成功，服务登记目录放在沙箱外且未重复写入。另行实测执行根目录的 `.git` 只读，嵌套工程的 `.git` 可写；不把这个结果外推到其他沙箱配置。官方 [权限配置说明](https://learn.chatgpt.com/docs/permissions#extend-a-profile) 解释了执行根目录受保护路径。
- 202 个源码文件的无 hook 临时工程：首次保存约 74 ms；10 次单文件稳定保存的中位数约 27 ms、最大约 29 ms。该结果仅反映本机小型夹具，真实工程、签名和 hooks 可能更慢。
- 仓库完整回归、独立插件构建检查、Claude 插件校验及两份插件 manifest 一致性检查均通过。后续代码变化仍需重跑相应检查。

以上为 2026-10-17 的源码与临时仓库验收；当时尚未接入真实 App 工程和远端。当前实现不承诺每次按键保存、不负责任意源码中的秘密扫描，也没有实现阶段验证和开发分支发布。
