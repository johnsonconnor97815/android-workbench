## 已确定的主流程

1. 分析全库架构，识别模块、SDK、权限、进程、入口、类、方法、原生库、资源和其他代码载体，确定复制、复用和待还原范围。
2. 从第一个入口开始，建立所需类结构并实现方法。沿构造、初始化、继承和调用关系逐步展开；遇到后续方法时才登记和委派。
3. 达到第一个明确的可运行阶段后，运行原 App 和复制 App，比较约定的状态和行为，验证实现者把握不高的函数。
4. 继续其余入口及阶段，复用已经实现或正在处理的类和方法。
5. 对照全库清单查找剩余代码，判断遗漏场景、新入口、复用或等价覆盖、可排除代码、待确认项。未从已知入口到达不等于无用。
6. 交付 App、阶段验证结果、无用或可排除代码清单及依据，并明确未解决事项。

MVP 是小范围、能运行的阶段交付，例如完成启动并进入首屏。它不缩减最终范围，也不要求把第一个入口能够通往的所有后续业务全部做完才能首次运行。后续分支继续登记。

入口有多个，不能只识别桌面 Activity。记录 Application 初始化、组件生命周期、Activity/别名/深链接、Service/Receiver/Provider、通知、后台任务、外部调用和后续发现的动态、原生、脚本入口。入口触发方式和共享实现分别记录。

## 已认可的五种角色及职责边界

角色与实例数量分开。不会让五个长期存活的实例包办整个 App；按有明确归属的任务启动、恢复或交接实例。

| 角色 | 责任 | 交付 |
| --- | --- | --- |
| Main | 接收用户要求和范围调整，说明进度、问题和结果 | 用户要求记录、进度、最终报告 |
| App 负责人 | 确定范围与 SDK 取舍，安排入口和 MVP，调度任务，协调跨任务问题，核对整体覆盖 | 复制计划、任务安排、阶段结论和覆盖清单 |
| 分析 Agent | 工具辅助的初始架构盘点，以及具体疑难代码或未知入口的调查 | 架构清单、来源证据、专项还原结果 |
| 类 Agent | 指定类的声明、继承、接口、字段、初始化关系及跨方法一致性；Astra 决定结构，Sol 执行类声明和代码组装 | 类结构、关系记录、初始化安排、组装产物 |
| 方法 Agent | 指定方法体及必要局部逻辑的实现、自查、适用验证，发现后续调用并申请委派 | 方法产物、新依赖、验证结果、具体未知项 |

App 负责人看范围、关系和进度摘要，不把全 App 源码放进自己的上下文。程序承担编号、去重、领取、文件归属、记录和统计，普通方法无需逐个申请 App 批准。

分析 Agent 不为每个方法预先讲解源码。类和方法 Agent 可以使用现有 Skill 自行读取相关代码。只有具体疑难才创建分析任务。

每个类有唯一结构负责人，由 Astra 承担结构判断；Sol 承担该类的代码落地。实例负责一个类或紧密关联的小组，读取必要的父类和接口信息；不会负责全 App 结构，也不逐个审阅全部方法体。角色负担重时应分开实例的负责范围，不能取消类关系的责任人。

### 类关系、共享状态和非类产物

类关系由程序保存到共享记录，类 Agent 对自己类的语义和复制表达负责。记录原始标识、所属代码载体、父类、接口、成员归属、覆盖关系、来源及复制名称映射；未知关系不能当成确认事实。

子类负责人读取父类声明，父类字段由定义它的类负责人维护。子类不能重复定义继承字段来绕过结构缺失。覆盖关系、super 调用、动态分派及初始化关系均须按原代码处理。

构造器和初始化代码体可以委派方法 Agent；初始化归属和执行关系由类 Agent 维护。父类构造器调用子类覆盖方法等情况必须按原代码实际状态实现，不能凭习惯提前初始化。

| 对象 | 归属 |
| --- | --- |
| Package、模块组织 | App 负责人确定组织和映射；具体配置进入工程结构任务 |
| 类字段、静态字段、相关共享状态 | 定义它的类 Agent |
| 原生全局状态、结构体和接口 | 对应原生模块结构任务 |
| Java、Kotlin、原生、脚本函数体 | 方法 Agent |
| Manifest、构建配置、SDK 接入 | 单独分配工程结构任务 |
| 布局、图片、字符串和其他资源 | 按目录或模块分配资源结构任务 |

工程、资源和原生模块结构任务采用类 Agent 的专项任务模式，各自有明确文件范围和实例，不集中到入口类负责人身上。Package、Global、Class、Function 是对象层级，不分别增加一套常驻管理 Agent。

### 方法实现规则

先取得必要的类声明，再实现当前方法；不要求先完成整个类所有方法体。小且紧密相关的类可以一次交付，复杂类沿调用展开。

方法任务提供原代码及来源、相关字段和继承声明、被调用签名、资源/常量、名称映射、输出归属和具体疑问。允许按需读取源码，不因材料包没包含就反复要求其他 Agent 转述。

调用者不必等待被调用方法实现完成。只有缺失信息确实影响当前写法时才等待。相互引用或递归先建立必要声明，再分别实现，避免互相等待。

允许使用可读名称；反射、JNI、序列化等外部名称连接需保留或同步映射。VMP 和动态加载逻辑可以还原成普通代码，但应保持相关功能、调用、状态和对外效果。未实现部分不能用默认返回值冒充完成。

## 已确定的验证与并发约束

没有独立的核对放行 Agent。每个 Agent 负责自身交付，使用原代码及已明确要求自查；构建、接口检查和必要用例由工具执行。

MVP 验证绑定具体版本、触发条件、设备/应用状态和观察目标。必要时使用受管 Frida 等现有工具，观察输入、返回值、异常、相关状态变化、后续调用和线程关系。控制或记录时间、随机和网络因素。

差异记录应给出复现条件、两边表现和证据。方法问题交原方法任务，结构问题交所属类，漏入口或还原问题交分析，范围/SDK 选择问题交 App。暂时不能定位则明确已定位到的范围，不凭感觉要求重写。

运行反例也可验证原分析和 Skill。确认工具有误时形成最小复现，交维护方修复，修复后重新处理受影响结果。运行阶段通过只代表对应范围通过。

并发必须沿实现过程中发现的依赖展开，不能先把整张调用图全部派出去。所有实例共用宿主实际允许的并发额度，同一实现去重，已有成果复用，无空位则排队。调用关系不自动等于执行等待关系。

同一个最终文件保持单一写入负责人。同类方法可并发产出独立片段或补丁，工具做机械组装，类负责人处理结构冲突。

确实等待结构或其他任务时保存进度并释放实际执行名额；不是让仍占槽位的父任务空等子任务。超时、静默或通知丢失不证明旧实例已停止；确认停止写入后才重新分配。

## 用户明确要求：不得人为削减上下文额度

“提供足够上下文”指提供完成任务需要的信息，不是分配一个拍脑袋的 Token 预算。

- 不额外设置无依据的上下文 Token、提示词字符数或材料读取上限。
- 不根据估计的上下文占用提前压缩、截断、结束子 Agent 或强制换实例。
- 不因“材料预算用完”禁止读取相关源码。
- 按真实职责、代码对象和依赖分工，不按猜测的 Token 数切碎任务。
- 使用模型与宿主实际提供的容量；实际遇到平台限制时，依据真实情况保存进度并恢复。
- 并发名额与上下文容量是不同事项，不能用限制并发的理由另加上下文限额。

原始材料、结构和任务记录持续保存，用于压缩或中断后的恢复；保存记录本身不是提前削减上下文的理由。规划判断使用 Astra，代码实现使用 Sol，具体职责见下文；实际不可用须报告，不静默替换。缓存效果以真实记录为准，不作保证。

## 已确定的模型分工与思考强度建议

用户明确指定：代码实现使用 Sol，规划判断类工作使用 Astra。此处按工作性质分配模型，不是只把名称中带“类”的 Agent 交给 Astra。此前“核心任务都先用 Sol、疑难才换 Astra”的建议已被这一决定替代。

以下模型分工已确定，思考强度仍是初始建议，尚未经过本项目对照测试。high 表示较高思考强度，xhigh 表示更高强度；这是推理投入设置，不是额外的上下文额度，也不改变按需读取源码的权利。

| 角色或任务模式 | 模型 | 建议思考强度 | 负责的工作 |
| --- | --- | --- | --- |
| Main | 跟随用户会话配置；当前约定为 gpt-6.1-sol | 当前约定为 xhigh | 用户交互和报告；复制规划与技术判断由对应 Astra 任务承担 |
| App 负责人 | gpt-6-astra | xhigh | 范围、SDK 复用、跨入口安排、任务规划和剩余代码归宿 |
| 分析 Agent | gpt-6-astra | xhigh | 架构分析、代码语义还原、未知入口及具体疑难判断；机械盘点由工具完成 |
| 类 Agent 的结构职责 | gpt-6-astra | xhigh | 继承、接口、字段归属、初始化关系、动态分派与跨方法结构决定 |
| 类 Agent 的代码落地任务 | gpt-6.1-sol | high | 按结构记录实现类声明、组装代码和修复；工程、资源及原生模块代码落地同理 |
| 方法 Agent | gpt-6.1-sol | high | 方法实现、后续调用发现、自查和具体验证 |

表中类角色列出两种任务模式，角色总数仍为五种。每个类只有一个 Astra 结构负责人；最终类文件指定一个 Sol 写入者。该 Sol 可以同时实现本类的方法，接收其他方法任务的独立补丁并组装。沿用已有实例或按需分配执行任务，不要求每个类常驻两个 Agent。

Astra 的结构决定写入原有类记录，Sol 直接据此实现。普通实现仍由 Sol 理解源码、处理实现细节和自查；不能把写代码时的每一次判断都变成 Astra 请求。只有新发现影响既有结构决定，或出现具体未解语义时，才把问题交给相应 Astra 类或分析任务。Astra 不逐方法核对放行。

可选的信息提取任务继续建议使用 gpt-6-luna / low，职责见下文“已认可的读写分工”。它不是第六种常驻角色，不接管核心语义决定。文件读写、编号、去重和状态维护由程序执行。

### 思考强度与问题转交

- 已识别的复杂代码实现可以一开始使用 Sol / xhigh，例如语义已还原的虚拟机保护（VMP）逻辑、Java 与原生代码交叉的实现，以及复杂并发状态。无需强制先用 high 失败一次。
- 架构或语义判断直接交相应 Astra 任务，不要求先由 Sol 反复调查。实现者遇到具体未知时，交接原始来源、已有实现、疑点、已排除解释和验证结果；不能仅凭“调查时间长”或“一次工具失败”反复转交。
- 缺少代码载体、工具结果或运行证据时，先取得所缺材料；增加思考强度不能把未知事实变成已知。普通编译错误先按报错修复。
- 较低思考强度可以作为后续明确简单任务的候选配置；是否调整默认值，以相同材料下的实际交付与具体验证结果决定。不能借此改变用户已经指定的模型分工，也不凭方法行数或猜测成本自动降档。
- max 不作为默认设置。思考强度不是必须依次经过所有档位的重试流程，也不形成逐方法审批。

### 配置与执行记录

用户明确指定优先，其次是已允许的任务级选择，再其次是角色默认值。任务记录模型、思考强度及改变原因；启动程序将它们传给后端的实际配置接口，不能只在提示词里写“请使用某模型”。设置变更用于实际支持的后续执行；不支持原地切换的后端按正常交接处理，不能让新旧实例同时写同一产物。

当前宿主的子 Agent 接口声明支持 model 和 reasoning_effort；独立工作者可以使用新上下文并读取任务材料。全历史继承与显式模型覆盖的兼容性受宿主限制，不能假设任意组合都支持。配置被接受、后端报告采用何种配置、实际交付通过是三件不同的事：执行记录分别保存请求值和后端可核实值；后端未提供的信息标为未知。不可用或不支持时明确报错，不静默换模型或忽略思考强度。

2026-10-15 查询的官方页面列出 Sol、Astra 的 low、medium、high、xhigh、max，以及 Luna 的这些档位和 none；当前宿主还声明了部分模型的 ultra。此处建议只用两处均列出的 low、high、xhigh，不将宿主额外档位当作通用 API 能力。模型窗口大小也不代表每种宿主都提供相同可用容量。[Sol](https://developers.openai.com/api/docs/models/gpt-6.1-sol)、[Luna](https://developers.openai.com/api/docs/models/gpt-6-luna)、[Astra](https://developers.openai.com/api/docs/models/gpt-6-astra)

官方模型选择指南将 Astra 用于要求高的复杂分析、Sol 用于复杂技术工作、Luna 用于明确的信息提取，并建议用相同输入试验模型与强度。上表遵循用户指定的模型分工，结合职责提出思考强度建议；不是官方对这五种角色的指定方案。后续在已计划的复制任务和 MVP 中记录交付结果、返工、耗时及可取得的用量；不另设主观核对门禁，也不宣称便宜的单次调用必然降低整个任务成本。[Model selection](https://developers.openai.com/api/docs/guides/model-selection)

## 文件交互设计与已实现协议

用户进一步指出，Agent 交互应写入文件，并明确文件协议和意义。此前“直接沟通”不能解释为靠临时聊天决定任务、类结构或完成状态。

本项目建议：正式请求、答复、决定、状态和交付全部持久保存；宿主的消息和任务启动能力只负责通知及安排执行。读取通知后仍以对应文件和当前版本为准。通知丢失不丢工作，通知重复不重复执行，压缩后可从文件恢复。

这一方案适合当前共享工作区；不是声称所有多 Agent 框架都要求 JSON 文件。也不要求所有问题都经过 App Agent 口头转发：按类或任务归属直接投递持久请求即可。

### 文件各自表示什么

以下布局已实现，运行数据放在分析项目的复制工作区，不把真实 APK、运行证据或凭据提交到插件仓库。

| 文件或目录 | 意义与写入归属 |
| --- | --- |
| project.json | 范围、当前入口/MVP、SDK 取舍及用户要求；由 App 的明确决定更新，Main 的用户变更也须记录来源 |
| inventory/ | 原始入口、类、方法、资源及处理归宿；分析任务提供证据，程序维护索引 |
| classes/{class-id}.json | 类声明、关系、来源、版本和结构负责人；由所属类负责人提交更新 |
| tasks/{task-id}/task.json | 要做的事、原始对象、相关材料、输出范围、发现来源和真正的执行前置；程序按委派请求登记 |
| coordination/state.json | 运行状态、领取归属、活动实例和并发名额；调度程序唯一维护，Agent 不各自手改 |
| messages/{message-id}.json | 不可变的请求、答复、结构变更、交付或问题记录；含发送方、接收对象和关联任务 |
| artifacts/ | 各任务代码片段、补丁、分析材料和检查证据；任务只能写自己的产物范围 |
| mvp/{mvp-id}/ | 场景定义、对应版本、原 App 与复制 App 的观察、差异和结论 |

文件布局中的任务状态、调度状态和交付记录不能互相成为冲突的状态来源。领取和活动名额以 coordination/state.json 的受保护更新为准；任务定义和不可变消息记录说明“为什么做、做了什么”。界面或汇总表由这些记录生成。

记录格式应有协议版本、对象或任务标识、来源与产物引用；答复关联原请求。类变更包含依据的结构版本和具体修改。字段按消息种类提供，不能把所有字段强加给每次交互。

Agent 通过少量记录操作提交业务信息，程序填充编号、归属、时间及检查机械一致性。不能让 Agent 手写大批登记脚本或反复猜枚举；也不能把文件协议变成方法实现前的独立审核合同。

### 已认可的读写分工：不设置 Luna 中转 Agent

用户已认可：文件读写和机械维护由程序或工具执行，不单独设置一个 Luna Agent 负责所有文档出入。

| 工作 | 责任主体 |
| --- | --- |
| 决定任务内容、类关系、实现结论、未知项及证据含义 | 对应的 App、分析、类或方法 Agent |
| 读取指定记录，写入提交内容，检查格式、编号、版本、归属和锁，去重及更新状态 | 确定性程序或工具 |
| 从不规整的日志或文档提取有明确目标的信息 | 工具足够时直接处理；确有语言理解需要时，可委派 Luna 专项任务 |
| 生成索引、数量及进度表 | 程序从持久记录汇总；Main 或 App 解释具体问题与进度 |

Luna 提取结果必须关联原文位置或证据，缺失和不确定内容如实返回。涉及复制范围、类关系、调用语义或完成结论时，原职责负责人依据原始证据作出决定；不能把提取摘要自动提升为已确认事实。

程序的格式检查只证明记录能被正确读写，不证明业务内容正确。交付者继续对含义负责，具体效果通过已约定的自查及 MVP 验证。常规交互直接调用工具，不要求所有读取和写入先经过 Luna；是否委派取决于该次提取是否有帮助，不预设节省时间或成本。

### 六种交互及处理者

| 交互 | 发起者 → 接收者 | 文件必须表达的事情 |
| --- | --- | --- |
| 派发任务 | App 的安排或已允许的发现请求 → 对应角色 | 目标对象、材料位置、输出归属、所在阶段 |
| 发现后续调用 | 方法 Agent → 调度程序 | 调用位置、目标或待确认候选、已有声明；由程序去重、关联来源、按额度派发 |
| 结构请求/答复 | 方法或子类任务 → 定义所属类负责人 | 缺失声明、具体问题或变更及来源；答复给出相关结构版本 |
| 专项还原请求/答复 | 实现任务 → 分析任务 | 确切未知点、已有材料、受影响对象；返回证据及仍未知的范围 |
| 交付 | 工作任务 → 所属类任务或阶段任务 | 产物引用、依据的结构版本、自查/检查结果、具体残余问题 |
| 阶段差异或范围决定 | 运行任务 → 责任任务；范围/SDK 问题 → App | 复现条件、两边表现、证据；需要 App 决定时说明具体选项与影响 |

普通源码读取不发送申请；已明确的规则由程序执行。结构负责人可以直接读取发给自己的文件请求，App 通过共同记录了解进度，无须每次中转。

### 一次调用发现的完整交互

1. 方法 A 的实现者发现调用 B，提交持久的依赖发现记录，指向原调用位置。
2. 调度程序确认 B 是已复用、已完成、正在执行，还是尚未登记。多个调用者发现 B 时保留多个来源，但只安排一个实现。
3. B 缺少必要类结构时安排该类任务；结构足够时安排 B 的方法任务。有空闲额度才启动。
4. 启动通知给出任务文件位置，B 的实现者读取材料，按需继续查源码。
5. A 不因“B 尚未完成”自动等待；B 的未知信息确实影响 A 时，A 记录需要的具体答复并保存进度。
6. B 的结果先保存为交付记录，再通知相关任务。负责该类文件的 Sol 读取片段及其依据的结构版本并组装；需要改变类结构决定的具体冲突交 Astra 类负责人。
7. 当前 MVP 所需交付齐备后运行比较，差异作为关联原任务的新记录进入修复。

继承关系示例：Base 的字段由 Base 负责人维护，Child 的继承/覆盖由 Child 负责人维护。Child 方法提出的父类字段问题通过文件投递到 Base，不直接改父类；答复发布后通知已登记的受影响任务。无法确认实际分派目标时创建具体分析请求。

### 文件协议必须解决的可靠性问题

- 同一对象只允许其负责人更新；记录提交检查所依据的版本，不能静默覆盖别人的新结构。
- 领取任务与占用全局并发名额必须是同一次受保护的状态更新，不能只给每个任务单独上锁。
- 写入使用完整发布机制，接收方不读取写到一半的 JSON；先保存产物，再发布引用它的交付记录。
- 请求使用稳定标识。恢复或重复通知时先查已处理结果，不能重复派工、重复应用补丁。
- 一组多文件操作中断时，恢复程序依据已持久的请求、产物和状态完成对账，不能宣称普通文件写入天然提供跨文件事务。
- 通知只负责加速发现新记录；启动和恢复时扫描尚未处理记录。检查由程序执行，不能让 LLM 反复轮询消耗调用。
- 发消息不等于接收者已经开始处理。正在执行的实例接收更新通知；空闲实例需要由调度器使用实际支持的继续任务或启动接口。OpenAI 文档中的 send_message 不开启新回合，followup_task 才可对空闲目标开始或恢复工作，后端适配必须区分这两种能力。
- “消息已写入”“任务已领取”“代码已交付”“阶段运行通过”分别记录，不能相互替代。
- 真实实例仍在执行或停止状态未知时保留归属。等待有依赖与平台上下文限制分开处理，不用上下文估算提前撤销实例。
- subagents、agent team 等底层机制只承担实际启动、通知和生命周期；项目文件协议保持一致。实际启动能力和环境限制按测试证据单独记录。

这些是交互正确性的设计条件，不新增 Agent 角色或逐方法批准流程。JSON 格式并不自动保证消息含义正确，具体答复仍由职责明确的 Agent 提供。

## 官方资料与研究结论

研究日期：2026-10-15。文件交互研究使用官方文档，并通过 Exa 和 Context7 辅助检索、定位；模型选择另查阅了上文链接的 OpenAI 官方页面。未采用第三方仿制项目或未公开源码分析作为机制事实。

- Claude Code 的官方 Agent Teams 文档同时描述共享任务列表和消息机制：信箱是本地 JSON 文件，发送成功以写入成功为条件，任务领取使用文件锁。官方也区分可保留的任务目录和会随会话结束清理的团队运行目录，因此不能把运行信箱当作永久项目档案。[Agent Teams](https://code.claude.com/docs/en/agent-teams)
- LangGraph 将单个线程的状态检查点与跨线程共享存储分开，持久后端支持恢复；内存保存不等于重启后仍存在。它支持数据库等存储，并没有要求所有通信都采用 JSON 文件。[Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)
- LangGraph 的恢复说明提醒，中断后的节点可能重跑，副作用需要能安全重放。这里借鉴请求去重和恢复原则，不引入其示例中的人工审批流程。[Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)
- OpenAI 的官方多 Agent 文档提供创建、发消息、等待、继续任务、中断和查看状态等协作动作；这些启动与通知能力不能代替本项目的类归属和交付协议。[Multi-agent](https://developers.openai.com/api/docs/guides/responses-multi-agent)

结论：官方实践支持有协议的通信、明确共享状态、可恢复交付和并发协调；没有“只能直接聊天”或“所有系统必须使用 JSON 文件”的统一规定。针对本项目选择持久文件作为交互依据、消息仅作通知，是基于共享工作区与恢复要求作出的设计建议。
