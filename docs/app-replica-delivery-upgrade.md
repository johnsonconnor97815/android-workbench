# 复制流程更新：交付内容复用与后续验证

本次更新修改 Workbench 调度程序和角色规则，不修改复制 App 的方法实现。发布工具与同事切换正在运行的任务是两个步骤；GitHub 已有提交，不代表同事已经采用。

## 改动与边界

- 源代码可以先交给组装者；后续组装、构建、运行核对登记到已有责任任务，不反向阻止源代码交付。当前方法缺失的逻辑、失败或未知检查仍阻止交付。
- 新依赖使用 `delivery_token`，绑定实际产物、类声明、检查输入和所用依赖。恢复/停止等状态变化不再单独使内容失效。真实变化、活跃写入和失败仍阻止复用。
- 普通交付直接到组装者；App 处理范围、冲突与实际阻塞。已有原版分析按载体散列、对象、问题和条件复用；出现新疑点或反例才补分析。
- 后续待办由程序保留，不能在下次提交中省略来消除。明确覆盖、对应检查和实际证据齐备后，组装/构建在真实停止时自动结项；运行待办还需要指定范围的成对 MVP。细节见[命令与字段](../skills/android-workbench/components/app-replica/README.md#按内容复用交付与后续验证)。

没有保证固定提速比例。报告或检查内容改变也会保守地改变 token；未登记的外部环境变化不会自动被发现。原版事实可复用，不代表变化后的候选代码自动通过。

## 更新顺序

1. 维护者先完成实现、测试和 GitHub 推送，提供精确提交号。
2. 当前复制负责人停止新派发，让活动任务保存检查点并正常收尾，核对真实进程/宿主实例及其写入后代。
3. 在当前工作机器备份最新源码与工作记录；不得用审计者的旧 Release 快照覆盖。
4. 当前复制负责人更新项目实际绑定的 Workbench checkout，确认新程序和新角色说明已经被使用。
5. 在旧记录上只做状态核验，再选一个实际待办验证新交付流程，之后恢复原有单一调度器。

不需要 schema 2/3 批量迁移。旧失败/未知记录不变，旧 revision 依赖保持严格检查；不要为了接入新字段批量唤醒所有已完成方法。原负责人下一次确有工作时，在已有证据基础上有针对性地换用 token。

现有 CLI 的 Ctrl-C 只退出派发器，**不会证明工作者已停止**；`step/run` 会派新任务，不能拿它们当只收尾的命令。原生模式则停止新的 `native-next` 与宿主派发。收尾仍由当前负责人使用已有后端的实际观察和 `run.stopped` 记录完成，不能伪造停止或释放其他宿主的名额。目录迁移和服务 drain 也不能代替复制工作者停止证明。

## 给同事的提示词

以下按顺序发给当前负责复制的会话。`TARGET_COMMIT` 替换为维护者最后交付的完整 Git 提交号。每一步的输出供下一步核对，不要一次性跳过检查。

### 1. 暂停派发并保存当前进度

```text
准备更新 android-workbench 的复制交付流程。请先停止派发新的复制任务，暂时不要更新工具，也不要恢复任何旧快照。

识别当前 App 工程、workflow 路径、实际 Workbench checkout 和后端类型。列出正在运行/尚未确认停止的 run、任务负责人及写入文件。让现有工作者在稳定边界保存代码、检查结果、未完成事项和继续位置，然后正常提交或保存等待检查点并结束本轮。

用当前宿主或 CLI 后端的实际证据确认实例和写入后代已经停止，再通过正式接口登记 run.stopped。仅消息说完成、没有输出、超时、目录改变或找不到旧 PID 都不算证明。保留原文件负责人、检查失败和未知项，不启动替代写入者，不重置状态。CLI step/run 会继续派发，不能拿来作为只收尾的操作。

完成后报告：实际路径与后端、旧 Workbench 提交号、最新 App 提交号、所有 run 的停止核对结果、仍未确认的实例、检查点位置。若还有不能确认的写入者，保持暂停并说明具体缺口，不宣称已经安全停止。
```

### 2. 备份这台机器上的最新工作

```text
基于上一步确认已经停止的当前工程制作更新前备份。先核对未提交改动和每个文件的归属，保留同事的新代码，不 reset、不 clean、不用旧 Release 覆盖当前目录。

通过项目现有 Git 保存入口保存已稳定的 App 源码，并核对实际远端结果；git-flush 返回只表示已请求推送。保留最新 workflow 状态、任务产物、协作记录、分析与检查点。若当前 Avola 工程提供 migration/sync.py，按其 README 使用 python3 migration/sync.py --require-idle；核对生成的快照、附件校验、App 与 Workbench 提交号、workflow revision、active_run_ids 和 handoff_ready。上传失败不能算已有远端备份；原有本地文件仍保留。

报告备份位置或 Release 地址、源码提交号、workflow revision/文件散列以及确认没有活动写入者的依据。备份成功后继续保持暂停，尚不启动任何复制工作。
```

### 3. 更新工具并核对实际入口

```text
现在更新到 android-workbench 的 TARGET_COMMIT。先核对项目 workbench.project.json、workflow/project.json（如有搬迁则读取正式路径绑定）及实际启动命令，确定真正使用的 checkout。不要只更新 App 仓库或已安装插件缓存。

在该 Workbench 仓库执行 git status --short、git fetch origin，确认 TARGET_COMMIT 可取得并核对改动。工作树干净且可快进时，用 git merge --ff-only TARGET_COMMIT 整合；若有本地修改、分叉或后续提交，先保留并核对兼容性，不 reset --hard、不强推。读更新后的 docs/app-replica-delivery-upgrade.md、app-replica 协议和当前角色说明。

运行 python3 scripts/check.py。它已包含插件构建检查；claude 可用时再运行 claude plugin validate .。失败则保持暂停并修复，不启动复制任务。

长驻进程、已安装副本和旧 launch prompt 不会因 Git 更新自动换代码。重新进入使用该 checkout 的调度入口，后续任务必须读新版角色规则。若实际使用安装版共享服务，先确认共享受管工作已经收尾，再按现有 scripts/upgrade_runtime.py --project 实际项目路径 --skip-project-update 切换；不要因此中断其他设备任务。直接使用源码 CLI 的流程无需为了更新角色规则重装整套设备环境。

用该 checkout 的 scripts/app_replica.py --workspace 实际workflow路径 status --summary 核对 delivery_protocol:2、occupied:0、任务数量、原有失败/未知项、Git 状态和 followup_counts。这一步不派发任务、不手改状态、不批量迁移，不恢复旧快照。报告实际执行路径、提交号和检查结果。
```

### 4. 用一个真实待办验证，然后恢复推进

```text
使用当前最新记录，选择一个本来就需要推进、且已有明确组装负责人的方法，验证新版交付流程。不要为了演示重做所有已经完成的方法。

先查已有原版分析与类声明。载体散列、对象、问题和条件仍适用就直接引用；只有新疑点、输入变化或反例才补分析。读取已完成依赖时保存它的 delivery_token，提交时用当时实际使用的 token，不临提交时抄最新值。类声明仍记录实际使用版本，相关构建/检查配置用 inputs 绑定散列。

方法确已实现且当前自查通过时，以 scope:source 交付。未实现逻辑、占位和失败/未知检查仍保留为阻塞。未来组装/构建/成对运行事项登记 followups，给出已有责任任务、具体条件和证据；运行待办还须明确 runtime_scope。不要把原有 unresolved 自动清空：逐条核对，确属下游工作才在新交付中明确转交，并保留原历史和依据。

组装者读取片段及 token，在交付中明确 addresses_followups，提供对应 stage 的检查与证据。程序确认成功停止后会自动结项组装/构建；运行待办在实际成对 MVP 通过后再用 followup.resolve 关联，宿主模拟不能代替 Android 范围。查看 followup_results/current_status，未结项就保留具体原因。

核对这个方法能够交给组装者，同时未验证事项仍在记录中；没有重复负责人、没有为了普通完成重复唤醒 App。状态变化本身不应要求重写代码，真实代码/声明/证据变化仍应使受影响结果失效。

完成后报告这一条实际链路的结果，然后恢复原有单一调度器和原并发/模型分工，继续完整复制范围。不要新增另一套执行器。后续按需采用新字段，不批量重跑旧方法；分别报告实现、构建、安装、运行与原版比较。
```

### 5. 若切换后发现问题

```text
先停止新派发，保存当前工作和真实运行证据，确认写入者收尾。不要用更新前快照覆盖已经新增的源码或任务记录，不强行把旧程序接到已经写入新格式交付/followups 的工作区。

记录失败命令、退出状态、实际工具提交号、受影响任务及最小复现。优先在独立副本修复工具，再保留当前记录向前更新。只有确认切换后没有任何新格式记录或新工作写入，才可在停止状态下评估仅回退工具版本；存在新记录时需要专门兼容处理，不能直接 git checkout 旧版后继续写入。

报告哪些内容已经保存、哪些仍未知、需要维护者修复的具体问题。错误恢复不能把失败改成通过，也不能重做无关分析。
```

## 维护者验证范围

本仓库测试使用临时目录、模拟后端和明确标注的宿主观察。应覆盖内容相同/变化、传递依赖、活跃与失败运行、旧记录、文件/类/输入变更、待办归属与结项、成对观察范围和搬迁路径。完整检查使用 `python3 scripts/check.py`，其中包含 `python3 scripts/build_plugin.py --check`；另在可用时执行 `claude plugin validate .`。

这些检查证明工具协议的宿主行为，不证明 Avola 已构建、安装或与原版一致。当前同事工作区的备份、停止确认、升级和恢复结果，应由同事在执行上述步骤后记录；维护者推送代码不能代替这些结果。
